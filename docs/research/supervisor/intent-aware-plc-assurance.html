Why refocus now

A literature scan in September 2026 shows that an LLM that generates Structured Text and then checks it with a compiler and a model checker in a loop is already published: Agents4PLC appeared in IEEE TSE in 2026 [1]. Benchmarks with formal properties and reference solutions also exist: Agents4PLC v2.0 has 96 tasks, and another study uses 100 tasks with MatIEC, PLCverif and OpenPLC [1, 2]. A thesis that only reports "better generation" would therefore add little.

Research question

When a pipeline reports an LLM-generated PLC program as "verified", was it verified against a specification that actually captures the engineer's safety intent?

A model checker proves that the code satisfies a specification, not that the specification is complete. Here is an example with a motor, an emergency stop and a reset button. Take the specification G(E-Stop active → Motor off), and a faulty variant of the program that drops the reset interlock. The faulty variant still satisfies the specification:

ScanInputsMotor, referenceMotor, faulty variant
1Start pressed, E-Stop healthy11
2E-Stop activated00
3E-Stop released, no Reset01

This is an illustration, not a result. The variant restarts the motor without a Reset, and the specification cannot see it. The three-scan scenario is exactly the question we would put to an engineer: "Should the motor restart here?"

Hypotheses (falsifiable)

  1. H1. A non-trivial share of intent-violating safety faults survive independent specifications, that is, human-written benchmark specifications and LLM-generated ones.
  2. H2. In LLM generate-verify-repair pipelines, some outputs accepted as "verified" violate the intent, mostly because the specification is inadequate rather than because the verifier is wrong.
  3. H3. Showing engineers distinguishing scan-cycle scenarios raises specification adequacy with a small number of questions.

The thresholds are pre-registered before the main data collection. A refuted hypothesis is reported as a result.

Positioning: what is known and what would be new

Known, and we build on it

  • Mutation-based coverage for model checking [3], and model-checker counterexamples that distinguish mutants [4].
  • Measuring the completeness of LLM-generated specifications with mutants, for sequential Python and Java code [5].
  • Clarifying user intent through test queries (TiCoder) [6].
  • LLM plus formal verification for PLC code [1, 2].

New, to be confirmed by a systematic review

  • Measured specification adequacy and false assurance in LLM-based PLC pipelines, under scan-cycle semantics.
  • Safety mutation operators derived from real faults we observe in LLM-generated IEC 61131-3 code, including NO/NC polarity, reset and interlock faults.
  • An intent loop that engineers answer through timing scenarios, not temporal logic, and that is combined with counterexample-guided repair.
  • A benchmark track that scores specifications, not only code.

Method and ground truth

  • Specifications refer to input and output signals only. We measure them from independent sources: Agents4PLC's published specifications (Apache-2.0) and specifications generated by several LLM families.
  • Every behavioural difference has a witness scenario, replayed in two executors: a scan-cycle interpreter and MatIEC-generated C. Samples are cross-checked with two verifiers, nuXmv and ESBMC-PLC+ [7].
  • Whether a fault violates the intent is decided by people, never by a tool or an LLM. A second, independent control engineer labels at least 20% of the cases, and we report inter-rater agreement (κ).
